# G04 — checklist specification (stack-neutral)

**Category:** 4 Logic-heavy  |  **Primary baseline (G2):** B2  |  **Status:** written before any agent output exists.

**G2 intent:** Shopping cart: quantities, remove, promo code (one valid code), subtotal/tax/total

Source of truth for the checklist items: `docs/G2_Benchmark_Corpus.md` §5 (main @ 5fdd412). Item order and wording below follow the G2 row. **A** = automatable (decided by the checker from observables), **H** = human-judged: *not judged (D-5)*; pass is decided on A items only.

## Fixture

Sentence(s) to append **verbatim** to the intent text, for **both** stacks (needed so the A items can be evaluated; the G2 intent alone does not contain this data):

> The cart has three lines: "Notebook" $4.99, "Pen" $1.25 and "Backpack" $19.90, each starting at quantity 1, with a button named "Increase quantity" and one named "Decrease quantity" (the quantity never goes below 1) and a button named "Remove" inside its row. Below the lines there is a text field labelled "Promo code" with an "Apply" button. The only valid code is SAVE10, which takes 10% off the subtotal; any other code shows an error message containing the word "Invalid". The summary shows four lines labelled "Subtotal" (sum of all lines before discount), "Discount", "Tax" (8.25% of subtotal minus discount, rounded half-up to the cent) and "Total" (subtotal minus discount plus tax). All money is shown in dollars with two decimals, like "$4.99", and must be exact decimal arithmetic with no floating-point rounding errors.

## How the checks observe the app

All checks are predicates over the stack-neutral **Snapshot** (`PVC_CHECKER_NEEDS.md` §1) and a small event vocabulary (click, type, key, new session). Baseline: Chromium 141, offline, DOM geometry + Chromium accessibility tree. PVC: `pvc_runtime` headless. Geometry widths: 320, 480, 768, 1024, 1280 px; default height 800; text scale 1 unless stated.

**Locator conventions used by this specimen:**

- rows: line text = exact item name; per-row buttons named /increase|plus|+/ , /decrease|minus|−/ , /remove|delete/
- amounts: for labels Subtotal, Tax, Total the amount is in the same text node or the next money text in reading order within the same container
- promo field = text input named /promo|code|coupon/i; apply = button named /apply|redeem/i
- reference model in `core/specs/G04.mjs` uses integer cents with half-up rounding

## Checklist items

### G04.1 — Arithmetic exact in decimal  `[A]`  *(scripted interaction; replayed by keyboard in U2)*

**Operational definition**

- Fresh load. Check Subtotal/Tax/Total against the exact reference at four states: (1) initial (Notebook 1, Pen 1, Backpack 1); (2) after Increase on Backpack (qty 2); (3) after applying promo code SAVE10; (4) after Remove on Pen.
- A mismatch of even one cent in any of the three lines fails the item.

**Standardised failure text (the only repair feedback for this item, G2 §4.4):** `Not met: the subtotal, tax and total must be exact in decimal arithmetic (to the cent) after every change.`

### G04.2 — Invalid code error  `[A]`  *(scripted interaction; replayed by keyboard in U2)*

**Operational definition**

- Fresh load; Increase Backpack (qty 2) so the totals are non-trivial; enter promo code "WRONG" and press Apply. A visible message matching /invalid|not valid|unknown|not recognised|not recognized|incorrect/i that was not visible before must appear (an `alert`/`status` node or plain text), AND Subtotal/Tax/Total must be unchanged (no discount applied).

**Standardised failure text (the only repair feedback for this item, G2 §4.4):** `Not met: an invalid promo code must show an error message and must not change the totals.`
